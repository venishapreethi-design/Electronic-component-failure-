# Project Report: AI-Based Early Warning System for Electronic Component Failure

## 1. Abstract
This project builds an educational machine-learning pipeline that uses electrical measurements—temperature, voltage, current, resistance, and component type—to estimate the likelihood of a labelled failure event within 24 hours. It includes data validation, feature engineering, a Random Forest model, evaluation metrics, and a Streamlit dashboard.

## 2. Problem statement
Electronic components can degrade due to thermal stress, overcurrent, abnormal voltage, and changes in electrical characteristics. Detecting unusual operating patterns early can help an engineer inspect a component before a fault becomes disruptive. The objective is to classify each measurement as higher or lower estimated failure risk.

## 3. Objectives
- Collect or load labelled measurements.
- Clean invalid data and explore distributions.
- Engineer useful features such as estimated power and voltage/current ratio.
- Train and evaluate a classifier using a held-out test set.
- Present risk estimates in an interactive dashboard.

## 4. Dataset and collection
The supplied `generate_dataset.py` creates synthetic demonstration data with timestamps, component types, temperature, voltage, current, resistance, and a binary target `failure_within_24h`. The labels are generated from an illustrative rule with random variation. This allows the complete software pipeline to run without laboratory hardware. It does **not** represent a validated physical failure model.

For real data, collect measurements from safely operated test fixtures with calibrated sensors and a consistent sampling interval. Record component ID/type, timestamp, ambient conditions if available, measurements, and a verified outcome window. Label failure only using documented inspection or test outcomes. Store units, calibration details, and collection protocol. Never deliberately create unsafe electrical faults for this project.

## 5. Methodology
1. Validate required fields and convert measurements to numeric values.
2. Remove rows with unusable or physically invalid negative readings.
3. Engineer power \(P=VI\), \(V/I\) with a small denominator floor, temperature excess above 40°C, and log resistance.
4. One-hot encode component type and median-impute numerical features inside a scikit-learn pipeline.
5. Split data into stratified 80% training and 20% test partitions.
6. Train a class-weighted Random Forest classifier.
7. Evaluate using accuracy, precision, recall, F1-score, ROC-AUC, and confusion matrix.
8. Display risk probabilities and threshold-based warnings in Streamlit.

## 6. Metrics
- **Precision:** fraction of predicted high-risk cases that are truly labelled high-risk.
- **Recall:** fraction of labelled high-risk cases correctly detected.
- **F1-score:** harmonic mean of precision and recall.
- **ROC-AUC:** ranking quality across classification thresholds.
- **MAE/RMSE:** appropriate only if the target is a continuous value; this implementation is a classification task, so classification metrics are used.

Metrics are generated by `python -m src.train_model` and saved to `artifacts/metrics.json`. No fixed score is claimed here because results depend on the generated data and seed.

## 7. Expected output
The model artifact, metrics JSON, test predictions CSV, EDA summary, histograms, and correlation heatmap are created by the included scripts. The dashboard shows measurement rows, estimated risk probabilities, high-risk counts, and downloadable predictions.

## 8. Limitations
- Synthetic labels can cause deceptively good metrics.
- The model does not account for every component design, load, ambient condition, aging mechanism, or sensor calibration error.
- A probability is a model score, not a guaranteed probability of real failure.
- Random row splits may overestimate performance if measurements are repeated for the same component. For real deployment, use time-based and/or component-grouped evaluation and independently collected test data.
- Alert threshold should be chosen with engineering stakeholders based on false-alarm and missed-failure costs.

## 9. Future enhancements
- Use a real, independently labelled maintenance/failure dataset.
- Add rolling statistics, rate-of-change features, and component-specific operating limits.
- Evaluate using group/time-aware splits and calibration curves.
- Add alert logging, authentication, and a hardware sensor gateway.
- Compare Random Forest, Gradient Boosting, and a simple baseline.

## 10. Conclusion
The project demonstrates an end-to-end early-warning ML workflow, from dataset generation and preprocessing through model evaluation and dashboard-based risk display. It is suitable as a reproducible academic prototype. Real-world use requires validated data, rigorous evaluation, and electrical safety review.
